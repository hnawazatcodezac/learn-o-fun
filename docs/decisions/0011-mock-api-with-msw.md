# 0011. The mock API runs on MSW's service worker, in every build until a backend exists

- Status: accepted
- Date: 2026-10-20
- Plan section: 2.1 (components), 5.4 (interruptions); builds on ADR 0001

## Context

The frontend is built before the backend (ADR 0001), so every API call is answered by mock handlers that follow `packages/contracts`. Two choices were open: how the handlers answer the app's requests, and whether production builds include them.

## Options considered

How the handlers answer:

1. MSW's standard service worker, which intercepts the page's real network requests.
2. Handing each request to the handlers inside the page with MSW's `getResponse`, with no service worker.

Production builds:

1. Include the mock API until a backend exists, so a deployed build works on any tablet.
2. Development only, so production builds have no data until the backend exists.

## Decision

The team's choices: **MSW's service worker**, and **the mock API in every build until a backend exists**.

- `packages/mock-api` holds the handlers, the single data file (`src/data/mock-data.json`) and the mock database. `startMockApi()` from `@learnofun/mock-api/browser` starts the worker before the app renders. The worker script is `apps/web/public/mockServiceWorker.js`, generated by `npx msw init` and kept up to date by `npm install`.
- Requests outside `/api` pass through to the network.
- A build with `VITE_API_MODE=live` leaves the mock API out entirely. The default is the mock.
- The development-only control panel switches latency (normal, slow) and failure (none, offline, server error). The choice is saved in the browser and applies after the page reloads. Mock state is saved in `localStorage`, so a refresh keeps progress; the panel can reset it.
- When the browser reports it is offline, the handlers return a network error, so tests with the network switched off behave like a real outage even though the worker still intercepts requests.

## Consequences

- **Step 9 must combine service workers.** The PWA's own service worker and MSW's cannot both control the app's scope. When step 9 adds the PWA worker, it either imports MSW's script (`importScripts`) while the mock is on, or registers only in live builds.
- Production builds with the mock load MSW and the mock data as a separate file before the app starts: about 160 KB gzipped today. A live build drops it.
- The app's API client validates every response against `packages/contracts`, which puts Zod in the main bundle (about 30 KB gzipped). That check stays once the real API arrives.
- Revisit when the backend arrives (switch builds to `VITE_API_MODE=live`), or if the service worker clash in step 9 proves costly, in which case `getResponse` inside the page is the fallback.

## Amendment, 2026-10-21

Where a browser has no service worker, such as a tablet reaching the development server over plain HTTP, the mock API now answers from inside the page with `getResponse` (ADR 0017). The service worker stays the default everywhere it exists.
